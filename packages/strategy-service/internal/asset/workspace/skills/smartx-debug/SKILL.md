# SmartX Debug

这个 skill 负责 SmartX 策略的调试闭环。
它聚焦“启动 -> 看日志 -> 查文档 -> 定位 -> 修复 -> 再启动 -> 再看日志”的连续过程。
它只负责调试闭环本身；任务路由、协作选择与全局调度由 `smartx-helper` 负责。

进入调试前的第一步：
- 先阅读项目的 `README.md`。
- 先阅读当前技能目录下的 `references/pythonApi.md` 和 `references/pythonGetDtaApi.md`。
- 先确认策略名称、入口、依赖、配置和运行前提。
- 如果当前工作区里已有实现修改，先理解最近改动，再进入调试。

## 调试工具优先级

优先使用：
- `smartx_start`
- `smartx_logs`

要求如下：
1. 不手工拼 HTTP 请求，优先走现有工具。
2. 调用 `smartx_start` 前，先确认 `name`。
3. 每次启动成功后，立即调用 `smartx_logs` 查看最新日志。
4. 优先根据真实日志、真实报错和真实运行结果修复问题，不要盲改。
5. 如果错误与 SDK 用法、参数名、字段名、回调时机有关，先回到 `references/` 核对对应说明，再改代码。
6. 如果首次修复后仍有问题，继续执行“修复 -> 启动 -> 看日志 -> 查文档”。
7. 只有遇到明确外部阻塞时才允许停止。

## 调试中的文档约束

1. 不要根据经验猜 SmartX SDK 的接口名、参数名、字段名或生命周期。
2. 不要为了消除报错，擅自改成未在 `references/` 或工作区代码中出现过的 SDK 写法。
3. 如果日志暴露的是“不存在的方法”“参数不匹配”“字段缺失”“回调未触发”等问题，必须把对应 reference 查实后再修。
4. 如果 `references/` 没有覆盖当前用法，先查工作区现有实现；仍没有证据时，明确说明文档缺口，不要伪造补丁。
5. 如果文档、日志和现有代码互相冲突，要把冲突点说清楚，再做最小修复。

## 调试流程

### 1. 先复现

- 明确当前要启动哪个策略。
- 明确当前错误是启动失败、运行异常、日志报错，还是行为不符合预期。
- 先拿到最新错误证据，再决定改哪里。

### 2. 看日志定位

- 优先抓最近一次启动后的日志。
- 区分环境问题、配置问题、入口问题、SDK 用法问题和业务逻辑问题。
- 如果日志不足以定位，再补读相关代码、配置和 references。

### 3. 查文档再修复

- 如果问题需要改代码，修改时同时遵循 `smartx-develop` skill。
- 先确认将要修改的 SmartX 接口在 `references/` 中的真实写法。
- 优先做最小且正确的修复。
- 不要为了压掉一个错误，顺手重构无关逻辑。

### 4. 再次启动验证

- 修复后重新调用 `smartx_start`。
- 再用 `smartx_logs` 检查新日志。
- 确认是旧问题已消失，还是出现了新的阻塞点。

### 5. 持续闭环

- 只要还存在可继续推进的问题，就继续“看日志 -> 查文档 -> 修复 -> 重启”。
- 如果已经跑通，明确说明当前状态和剩余风险。
- 如果被外部系统、账号、权限、网络或依赖阻塞，明确说明阻塞点。

## 输出要求

调试任务结束时至少说明：
- 启动了哪个策略。
- 实际看到了哪些关键日志或报错。
- 对照了哪些 references 或本地证据。
- 修了什么问题。
- 当前是否已经跑通。
- 如果没跑通，卡在什么外部阻塞。

## 不要这样做

- 不要跳过启动直接宣称已经修好。
- 不要只改代码不看日志。
- 不要只看日志不查对应 reference。
- 不要凭猜测连续改很多处而不验证。
- 不要在存在可继续推进的日志线索时过早停止。
- 不要伪造 SmartX SDK 用法来“修复”问题。

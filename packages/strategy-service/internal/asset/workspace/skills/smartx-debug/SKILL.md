# SmartX Debug

这个 skill 只负责 SmartX 调试闭环。核心流程是：

启动 -> 看日志 -> 查本地依据 -> 修复 -> 再启动 -> 再验证

统一术语：

- “本地依据”指 README、references、工作区现有代码、配置和最新日志。
- “验证”指实际启动、日志检查和对运行结果的可执行确认。
- “外部阻塞”指账号、权限、网络、依赖、环境或外部服务不可用等导致无法继续闭环的情况。

进入调试前先确认：

- 已阅读 `README.md`
- 已阅读 `references/pythonApi.md`
- 已阅读 `references/pythonGetDtaApi.md`
- 已确认策略名称、入口、依赖、配置和运行前提

优先使用这些工具：

- `smartx_start`
- `smartx_logs`

调试规则：

1. 不手工拼 HTTP 请求，优先走现有工具。
2. 调用 `smartx_start` 前先确认 `name`。
3. 每次启动后立即查看最新日志。
4. 优先根据真实日志、真实报错和真实运行结果修，不要盲改。
5. 如果问题与 SDK 用法、参数名、字段名、回调时机有关，先核对本地 references，再改代码。
6. 如果需要改代码，修改时同时遵循 `smartx-develop`。
7. 只有遇到明确外部阻塞时才允许停止。

定位规则：

- 明确当前问题是启动失败、运行异常、日志报错还是行为不符合预期。
- 优先抓最近一次启动后的日志。
- 区分环境、配置、入口、SDK 用法和业务逻辑问题。
- 如果日志不够，再补读相关代码、配置和 references。

修复规则：

- 先确认将要修改的 SmartX 接口在本地 references 或工作区代码中有依据。
- 优先做最小且正确的修复。
- 不要为了压掉一个错误顺手重构无关逻辑。
- 不要伪造未在 references 或工作区出现过的 SDK 写法。

结束时至少说明：

- 启动了哪个策略
- 看到了哪些关键日志或报错
- 对照了哪些本地依据
- 修了什么问题
- 当前是否已经跑通
- 如果没跑通，卡在什么外部阻塞以及下一步

不要这样做：

- 不要跳过启动直接宣称修好
- 不要只改代码不看日志
- 不要只看日志不查本地依据
- 不要凭猜测连续修改很多处而不验证
- 不要在还有明确日志线索时过早停止

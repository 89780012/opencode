# SmartX Debug

这个 skill 负责 SmartX 策略的调试闭环。
它聚焦“启动 -> 看日志 -> 定位 -> 修复 -> 再启动 -> 再看日志”的连续过程，不负责通用身份描述。

当用户要求“写完并运行”、启动策略、排查启动失败、修复运行报错、根据日志持续修复问题时，使用这个 skill。

进入调试前的第一步：

- 先阅读项目的 `README.md`
- 先确认策略名称、入口、依赖、配置和运行前提
- 如果当前工作区里已有实现修改，先理解最近改动，再进入调试

## 调试工具优先级

优先使用：

- `smartx_start`
- `smartx_logs`

要求如下：

1. 不手工拼 HTTP 请求，优先走现有工具
2. 调用 `smartx_start` 前，先确认 `name`
3. 每次启动成功后，立即调用 `smartx_logs` 查看最新日志
4. 优先根据真实日志、真实报错和真实运行结果修复问题，不要盲改
5. 如果首次修复后仍有问题，继续执行“修复 -> 启动 -> 看日志”
6. 只有遇到明确外部阻塞时才允许停止

## 调试流程

### 1. 先复现

- 明确当前要启动哪个策略
- 明确当前错误是启动失败、运行异常、日志报错，还是行为不符合预期
- 先拿到最新错误证据，再决定改哪里

### 2. 看日志定位

- 优先抓最近一次启动后的日志
- 区分环境问题、配置问题、入口问题、SDK 用法问题和业务逻辑问题
- 如果日志不足以定位，再补读相关代码和配置

### 3. 修复问题

- 如果问题需要改代码，修改时同时遵循 `smartx-develop` skill
- 优先做最小且正确的修复
- 不要为了压掉一个错误，顺手重构无关逻辑

### 4. 再次启动验证

- 修复后重新调用 `smartx_start`
- 再用 `smartx_logs` 检查新日志
- 确认是旧问题已消失，还是出现了新的阻塞点

### 5. 持续闭环

- 只要还存在可继续推进的问题，就继续“看日志 -> 修复 -> 重启”
- 如果已经跑通，明确说明当前状态和剩余风险
- 如果被外部系统、账号、权限、网络或依赖阻塞，明确说明阻塞点

## 输出要求

调试任务结束时至少说明：

- 启动了哪个策略
- 实际看到了哪些关键日志或报错
- 修了什么问题
- 当前是否已经跑通
- 如果没跑通，卡在什么外部阻塞

## 不要这样做

- 不要跳过启动直接宣称已经修好
- 不要只改代码不看日志
- 不要凭猜测连续改很多处而不验证
- 不要在存在可继续推进的日志线索时过早停止
